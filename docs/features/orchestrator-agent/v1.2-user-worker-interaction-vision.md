# Orchestrator v1.2: User-Worker Interaction Vision

**Status**: Future Work (Post v1.1)  
**Target**: v1.2 or later  
**Last Updated**: 2026-01-30

---

## North Star Goal

**"User and AI Cowork: User owns real world, AI owns virtual world"**

Enable bidirectional, real-time collaboration between users and individual workers during task execution. Users can:
- Chat directly with any worker (orchestrator, backend, frontend, qa)
- Guide worker decisions through conversation
- Approve/reject worker proposals
- See workers thinking and working in real-time
- Intervene at any point during execution

Workers can:
- Ask users questions when uncertain
- Request approval for critical decisions
- Stream their thinking process to users
- Propose solutions and wait for feedback
- Collaborate with users as teammates, not tools

---

## Current State (v1.1)

### What Works Today
- ✅ User → Orchestrator conversation (plan creation/approval)
- ✅ Orchestrator → Workers task dispatch (autonomous)
- ✅ Workers execute tasks independently
- ✅ Event-driven architecture with WebSocket infrastructure
- ✅ Real-time message streaming from agents
- ✅ Frontend can subscribe to specific agents

### Limitations
- ❌ No direct user-worker chat during execution
- ❌ Workers can't ask users questions
- ❌ No user intervention during task execution
- ❌ Users only see final task outputs, not thinking process
- ❌ All worker decisions are autonomous (no approval flow)

## v1.2 Vision: Interactive Collaboration

### 1. Worker Chat Sessions

**Goal**: Each worker maintains a conversational thread with the user.

**User Experience**:
```
User: "Hey Backend worker, how's task-3 going?"
Backend Worker: "I'm implementing the API endpoints. Should I use 
                 REST or GraphQL for the task queries?"
User: "Use REST, keep it simple"
Backend Worker: "Got it, creating REST endpoints..."
```

**Technical Components**:
- Worker conversation state per worker instance
- Message routing (user message → correct worker)
- Worker response streaming to frontend
- Conversation history persistence

**Architecture Impact**: ✅ Compatible (InternalAgent already supports chat mode)

---

### 2. Interactive Task Execution

**Goal**: Workers can pause and ask for user input during task execution.

**User Experience**:
```
[Frontend Worker executing task-5: "Develop frontend UI"]

Frontend Worker: "I can implement the UI in two ways:
                  1. Material UI components (faster, opinionated)
                  2. Custom Tailwind CSS (more control, slower)
                  
                  Which approach do you prefer?"
                  
User: "Let's go with Material UI for speed"

Frontend Worker: "Perfect! Installing Material UI and creating components..."
```

**Technical Components**:
- `ask_user(question)` tool for workers
- `request_approval(proposal)` tool for workers
- Worker pause/resume mechanism
- Timeout handling for unanswered questions
- Default fallback when user unavailable

**Architecture Impact**: ✅ Compatible (add tools to worker agent definitions)

---

### 3. Real-Time Collaboration Stream

**Goal**: Users see workers' thinking process in real-time, can interrupt/guide.

**User Experience**:
```
[Backend Worker - Task 3: Implement API]

Worker: "Analyzing task requirements..."
Worker: "Planning endpoints: GET /tasks, POST /tasks, PUT /tasks/:id, DELETE /tasks/:id"
Worker: "Considering authentication strategy..."

User: [interrupts] "Use JWT for auth"

Worker: "Got it! Updating plan to use JWT authentication..."
Worker: "Implementing JWT middleware..."
Worker: "Creating protected routes..."
Worker: "Testing authentication flow..."
Worker: "✓ API endpoints complete with JWT auth"
```

**Technical Components**:
- Stream worker's internal monologue to frontend
- User interrupt mechanism during execution
- Message prioritization (user messages skip queue)
- Worker acknowledgment of user guidance
- Visual indicators (thinking, waiting, executing, blocked)

**Architecture Impact**: ✅ Compatible (already have worker:event emissions)

---

### 4. Approval Workflows

**Goal**: Workers propose solutions, wait for user approval before proceeding.

**User Experience**:
```
[QA Worker - Task 7: Write Unit Tests]

QA Worker: "I've created test suites for:
            - Backend API endpoints (Jest + Supertest)
            - Frontend components (React Testing Library)
            - Integration tests (Cypress)
            
            Total: 45 tests covering 85% of code.
            
            [Approve] [Request Changes] [See Details]"
            
User: [clicks "See Details"]

QA Worker: [shows test breakdown]

User: [clicks "Approve"]

QA Worker: "Tests approved! Committing to repository..."
```

**Technical Components**:
- Approval checkpoints in worker execution
- Structured proposals (with alternatives, pros/cons)
- User review UI (approve/reject/modify)
- Revision loop (worker updates based on feedback)
- Auto-approval for low-risk decisions (configurable)

**Architecture Impact**: ✅ Compatible (add approval tools, extend WorkerPool logic)

---

### 5. Message Routing & Context

**Goal**: Route user messages to correct worker, maintain conversation context.

**User Experience**:
```
User: "Backend, add rate limiting to the API"
        ↓
Backend Worker: "Adding rate limiting middleware..."

User: "Frontend, show loading spinner during API calls"
        ↓
Frontend Worker: "Creating loading component..."

User: "All workers: use consistent error messages"
        ↓
[Broadcast to all active workers]
```

**Technical Components**:
- Message parser (extract target worker from user input)
- Worker addressing (`@backend`, `@frontend`, `@qa`, `@all`)
- Context propagation (worker knows what user is referring to)
- Conversation threading (separate threads per worker)
- Smart routing (AI determines target when ambiguous)

**Architecture Impact**: ✅ Compatible (add routing layer in SocketServer)

## Architecture Extensions Needed

### Event System Enhancements
```typescript
// New worker events (v1.2)
worker.on("question", (data) => {
  // Worker asking user a question
  sendToUser({ type: "worker:question", worker, question, options });
});

worker.on("approval_requested", (data) => {
  // Worker requesting approval
  sendToUser({ type: "worker:approval", worker, proposal });
});

worker.on("thinking", (data) => {
  // Worker's internal reasoning (real-time stream)
  sendToUser({ type: "worker:thinking", worker, thoughts });
});
```

## Open Questions (To Resolve)

1. **Context Window Management**: How to handle long conversations without exceeding LLM limits?
   - Option A: Summarize old messages periodically
   - Option B: Use RAG to retrieve relevant history
   - Option C: Conversation branching/threading

2. **Multi-User Support**: What if multiple users talk to same worker?
   - Option A: Single owner per worker session
   - Option B: Collaborative mode (all users see all messages)
   - Option C: User roles (owner, observer, collaborator)

3. **Worker Autonomy Level**: How much should workers decide vs. ask?
   - Configurable per user? (beginner = ask everything, expert = autonomous)
   - Per task type? (critical = always ask, routine = autonomous)
   - Learning over time? (worker learns user preferences)

4. **Timeout Handling**: What if worker asks question but user doesn't respond?
   - Default to safe option (configurable)
   - Escalate to orchestrator
   - Park task and move to next

5. **Cost Management**: Interactive mode = more LLM calls. How to optimize?
   - Batch worker thinking into fewer API calls
   - Cache common questions/responses
   - Use cheaper model for routine interactions
